# Data model

Source of truth: `supabase/migrations/`. This document explains the *why*; the SQL is
the *what*. Migrations are numbered, applied in order, and **never edited once pushed** —
change the schema by adding a new migration.

## The sync contract

Every syncable table carries the same five columns:

| Column | Rule |
|---|---|
| `id` | `uuid`, **generated by the client** so a row created offline keeps its identity forever |
| `user_id` | `uuid references auth.users`, the axis every RLS policy turns on |
| `created_at` | set once |
| `updated_at` | stamped by a trigger, **never** trusted from the device |
| `deleted_at` | soft delete; tombstones are pulled so deletes propagate |

`readora_make_syncable()` in `0001` attaches the trigger and the `(user_id, updated_at)`
pull index. Call it once per new table and the sync engine works without changes.

## Tables

### Shared

**`books`** — global metadata cache, one row per (source, source_id). Written only by the
`book-search` Edge Function using the service role; readable by any authenticated user.
Caching here means the second reader to scan an ISBN costs zero external API quota, and
it gives us a book identity that notes and concepts can hang off.

### Library

**`profiles`** — 1:1 with `auth.users`, created automatically by a trigger on signup.

**`user_books`** — the heart of the app. One row per book in a reader's library.
Notable choices:

- `rating` is stored as **half-star steps, 1..10**, not a float. Integers compare and
  aggregate cleanly and there is no half-star ambiguity.
- `page_count_override` exists because the edition a reader owns often differs from the
  catalogue metadata, and a wrong denominator makes every progress number a lie.
- unique on `(user_id, book_id)` **only where `deleted_at is null`**, so a reader can
  remove a book and add it again later.

**`shelves` / `shelf_items`** — custom shelves, many-to-many.

### Reading

**`reading_sessions`** — append-only. Each device writes its own rows and nothing ever
edits an old one, so sessions can never conflict during sync. `pages_read` is a
generated column, not a client calculation.

**`reading_days`** — one row per day the reader read anything. Streaks are **derived**
from this by `reading_streak()`, never stored as a counter: a stored counter cannot
survive offline edits, timezone changes, or a backfilled session. The function treats a
streak as alive if the last read day is today *or* yesterday, so the reader has all of
today to keep it.

**`goals`** — daily/weekly/monthly/yearly targets in minutes, pages, or books. One
active goal per (period, metric).

### Capture

**`notes`** — notes and highlights in one table, discriminated by `kind`. This is the
most precious data in the app: it is what makes the AI layer worth paying for and what
makes the reader's library impossible to replace. It is never hard-deleted from the
client. A trigger keeps `user_books.notes_count` accurate so the UI never has to count.

**`actions`** — "turn this book into practical actions" items, with `due_week` and
`completed_at`.

### AI

**`ai_threads` / `ai_messages`** — companion conversations, scoped to a book or to the
whole library (enforced by a check constraint).

**`quizzes` / `quiz_questions` / `quiz_attempts`** — knowledge-score history over time,
which is what makes quizzing feel like progress rather than a party trick.

**`flashcards`** — SM-2-lite: `ease`, `interval_days`, `reps`, `lapses`, `due_at`.

**`ai_usage`** — the monthly free-tier meter, one row per (user, month). **No client
write policy.** The only way it moves is `consume_ai_credit()`, a `security definer`
function that increments and checks the limit in a single atomic statement, so racing
two requests cannot buy a free credit.

### Knowledge (V2, schema ships in V1)

**`concepts` / `concept_links`** — the cross-book graph: a concept links to notes, books,
and other concepts with a relation (`supports`, `contradicts`, `extends`, `mentions`).

**`note_embeddings`** — pgvector, **server-side only, never synced to the device**. An
HNSW cosine index backs `match_notes()`, which powers *Ask My Library*.

These tables exist from day one deliberately: notes written during V1 are already
embeddable when the feature arrives, so the moat starts accumulating before the feature
that exposes it is built.

### Billing & diagnostics

**`subscriptions`** — one row per user, the only source of truth for paid access.
Written exclusively by the `revenuecat-webhook` function. There is **no client write
policy at all** — a user must never be able to PATCH themselves into Plus.
`has_active_plus()` is the helper every check goes through.

**`client_errors`** — insert-only from the client, with no select policy. The crash
sink while we ship without Sentry.

## RLS, in three tiers

| Tier | Tables | Policy |
|---|---|---|
| Owned | `user_books`, `notes`, `reading_sessions`, … | select/insert/update/delete where `auth.uid() = user_id` |
| Read-only | `books`, `subscriptions`, `ai_usage`, `note_embeddings` | select only; writes require the service role |
| Write-only | `client_errors` | insert only; no select |

The owned tier is generated from an array in `0009_rls.sql` rather than written by hand
per table, so adding a table to that array is the whole job — and forgetting is visible
in one place.

Hard `DELETE` is permitted on owned tables so the client can purge locally-created rows
that never synced. Normal deletion is a soft delete (an `UPDATE` of `deleted_at`).

## Local mirror (Isar)

Isar collections mirror the server tables, with a unique `uuid` index that matches the
server `id`. Two collections exist only on the device:

- **`OutboxEntry`** — pending change: entity, entityId, op, JSON patch, attempts, backoff
- **`SyncCursor`** — how far each table has been pulled

Enums are the one place the two schemas differ: Postgres uses snake_case enum values,
Dart uses camelCase. The mapping lives in `ReadingStatusWire` and nowhere else.
